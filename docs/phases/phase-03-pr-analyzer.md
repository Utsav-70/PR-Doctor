# Phase 3 — PR Analyzer

## Goal

Turn the raw fetched data into a structured, classified, measured description of the
change — and enforce the first cost budget. Entirely deterministic; no LLM.

## Depends on

Phase 2. **Unlocks** Phase 4.

## Scope

**In:** unified-diff parsing, per-file classification, line counting, diff position
mapping, path ignore rules, the changed-lines budget and partial-review mode.

**Out:** Symbol resolution and cross-file references (Phase 4). Any judgment about
whether a change is *good* — that is the reviewer's job.

## What gets extracted

```
PR #123
├── title                 "Add retry to payment capture"
├── description           PR body (markdown, untrusted — see Phase 12)
├── base_sha              a1b2c3d
├── head_sha              e4f5a6b
├── changed_files         7
├── added_lines           210
├── deleted_lines         80
└── files[]
    ├── payment/service.py    python      source        +84  −12
    ├── payment/client.py     python      source        +31  −4
    ├── auth.py               python      source        +12  −0
    ├── tests/test_pay.py     python      test          +58  −0
    ├── package.json          dependency  dependency    +3   −2
    ├── poetry.lock           dependency  generated     +18  −62
    └── README.md             markdown    documentation +4   −0
```

## Diff parsing

Parse each file's unified-diff patch into hunks. Per hunk, from the `@@ -a,b +c,d @@`
header, produce for every line: its type (`context` / `added` / `removed`), its line
number in the new file (null for removed lines), and its **diff position**.

Diff position is the thing that matters later. GitHub's review API anchors a comment to
an offset within the diff, counting every line including hunk headers, not to a file line
number. Compute the mapping once here and store it as `review_files.diff_line_map`:

```json
{"87": 34, "88": 35, "112": 61}
```

Getting this wrong in Phase 9 produces comments on the wrong line, which is worse than
no comment. Computing it here — in the deterministic phase, where it can be checked
against a real diff by hand — is what keeps that bug out of Phase 9.

Handle the awkward cases explicitly rather than discovering them in production:

| Case | Handling |
|---|---|
| Renames | `previous_path` set; `change_type = renamed`; diff may be empty |
| Binary files | No patch; `language = binary`; `reviewed = false` |
| Mode-only changes | No content change; `reviewed = false` |
| Deleted files | `change_type = removed`; no findings can anchor here |
| No trailing newline | `\ No newline at end of file` is not a diff line — exclude from positions |
| Truncated patch | GitHub omitted it; `reviewed = false`, reason recorded |
| CRLF | Normalise for analysis, preserve for position counting |

## Classification

Two orthogonal axes. Keep them separate — conflating them is why "is this a test file"
becomes hard to answer later.

**`language`** — how to parse it: `python`, `javascript`, `typescript`, `go`, `sql`,
`yaml`, `json`, `markdown`, `dockerfile`, `dependency`, `binary`, `unknown`.

**`category`** — what role it plays: `source`, `test`, `dependency`, `documentation`,
`config`, `generated`.

Resolution order, first match wins:

1. **Ignore globs** from `IGNORE_PATHS` and per-repo `.prguard.yml` → `reviewed = false`.
2. **Generated-file detection** — path patterns (`*.lock`, `*.min.js`, `*_pb2.py`,
   `dist/`, `build/`, `**/migrations/**`) *and* a content sniff of the first few lines for
   `@generated`, `Code generated by`, `DO NOT EDIT`. Generated files are counted but not
   reviewed.
3. **Test detection** — `tests/`, `test_*.py`, `*_test.go`, `*.spec.ts`, `*.test.js`.
   Tests are reviewed, but with a different lens: a missing assertion matters, a missing
   docstring does not.
4. **Dependency manifests** — `package.json`, `requirements*.txt`, `pyproject.toml`,
   `go.mod`, `Gemfile`. Reviewed by the security agent for supply-chain concerns; ignored
   by the performance agent.
5. **Extension mapping** for everything else.

Classification is table-driven in one module with the table as data, not `if` chains, so
adding a language is a one-line change. Where extension heuristics are genuinely
ambiguous, a cheap-model classification call is permitted (see
[04-llm-strategy.md](../04-llm-strategy.md)) — but it is a fallback, not the primary path,
and it must be cached by path pattern.

## Metrics

```
changed_files  = count(files where reviewed or counted)
added_lines    = Σ additions
deleted_lines  = Σ deletions
changed_lines  = added_lines + deleted_lines
```

Report both the raw totals (what a human sees on GitHub) and the reviewable subset
(excluding generated, binary, and ignored files). The budget below applies to the
**reviewable** count — a 4000-line lockfile change should not consume the budget for the
40 lines of real code beside it.

## The budget

The first cost control, and the reason this phase exists before any LLM code:

```python
if reviewable_changed_lines > settings.MAX_CHANGED_LINES:  # default 5000
    partial_review(reason="diff_too_large")
```

Partial review is a **prioritised subset**, not a truncation at an arbitrary index.
Rank files and take from the top until the budget is spent:

1. `source` files in languages with a Tree-sitter grammar available
2. Files matching security-sensitive path hints (`auth`, `payment`, `crypto`, `session`,
   `permission`, `admin`, `token`)
3. Remaining `source` files, smallest first — more files reviewed per token spent
4. `dependency` manifests
5. `test` files
6. Everything else: not reviewed

Then set `is_partial = true`, `partial_reason`, and mark the unreviewed rows
`reviewed = false`. Phase 9 states this plainly in the review summary: *"Reviewed 12 of
47 changed files (diff exceeds the 5000-line budget). Unreviewed: …"*. A partial review
that presents itself as complete is a correctness bug, not a UX detail.

Also short-circuit to `skipped` when the reviewable set is empty — a PR that only touches
a lockfile and a README gets no comments and no LLM spend.

## Persistence

Fill in on `reviews`: `title`, `description`, `changed_files`, `added_lines`,
`deleted_lines`, `is_partial`, `partial_reason`.

Fill in on `review_files`: `language`, `category`, `diff_line_map`, `reviewed`.

The output of this phase is the `PullRequestContext` object the rest of the pipeline
consumes — a plain Pydantic model, constructible from fixtures without a database, which
is what makes Phases 5–8 testable.

## Exit criteria

- [ ] Every changed file has a `language` and `category`
- [ ] Line counts match what GitHub displays on the PR
- [ ] `diff_line_map` verified correct against a hand-checked real diff
- [ ] Renames, binaries, deletions, and mode changes all classified without error
- [ ] Lockfile-only PRs are `skipped`, not reviewed
- [ ] A >5000-line diff produces `is_partial = true` with a sensible file selection
- [ ] `PullRequestContext` builds from a saved webhook payload with no DB and no network
- [ ] Zero LLM calls in this phase's traces

## Risks

**Off-by-one in diff positions.** The most likely bug in the phase and the hardest to
notice, because a comment one line off still looks plausible. Check the computed map by
hand against a real diff — specifically one where a hunk starts at line 1, and one with
three hunks in a single file. Those are the two cases naive position counting gets wrong.

**Counting generated files against the budget.** A `poetry.lock` change can be 3000 lines
and will silently consume the entire review budget for a PR whose real change is twelve
lines.

**Trusting the PR description.** It is attacker-controlled markdown that is about to enter
a prompt. It is stored as data here; Phase 12 handles neutralising it. Do not
"pre-clean" it now in a way that loses information.
